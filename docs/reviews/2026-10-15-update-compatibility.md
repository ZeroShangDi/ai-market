# 1.0.11 更新兼容性排查与发布

日期：2026-10-15，北京时间。

## 现场与确定的事实

- 用户在 1.0.10 中手工检查更新，收到「更新与当前应用、平台、架构、渠道或基座不兼容」。排查开始时，手机入口的签名清单仍发布 1.0.8（106），并非比本机更新的版本。
- 1.0.10 APK 与发布清单中的 AppID 均为 `__UNI__D608100`，包名 `uni.UNID608100`、渠道 `stable`、APK 架构 `arm64-v8a`，清单最低基座为 1。
- 原客户端先执行全部兼容判断，再比较版本；五类失败共用一句错误。架构只读取 `Build.CPU_ABI`，未检查原生返回值；版本号也直接 `Number(...)`，原生返回 null 会被当成 0。因此无法凭此提示断定手机处理器不兼容。页面版本名称还可回退为编译版本，不能据此证明原生身份读取正常。
- 本机没有连接 Android 真机，也没有该手机的身份字段日志；尚不能确认这次手机实际触发的是哪一个字段。未将模拟读取失败写成已证实的手机根因。

## 修复

- 优先读取官方支持架构列表 `Build.SUPPORTED_ABIS`，允许清单匹配手机实际支持的任意 ABI；列表不可读时再回退 `CPU_ABI`。静态查询返回无效值时尝试导入类读取，不把 null 转为字符串。
- 安装版本字段增加导入对象与 Android 9+ `getLongVersionCode()` 回退，仍以实际 APK 版本作为基座；读取失败明确报错，不使用资源版本伪造成功。安装权限检查的 SDK 读取失败同样明确停止。
- 应用标识、平台、渠道、架构、基座分别提示。调试基座明确要求正式包；不把调试或其他应用标识改写成更新源的标识。
- 旧版或同版清单不执行安装架构、最低基座拦截，结果为「已经是最新版本」。清单签名、应用、渠道、平台、包名及制品格式仍检查；新包必须满足支持架构和基座要求，下载后继续核对大小、哈希和同一签名。
- 通过统一 logger 的固定事件 `update/identity.read` 记录必要的应用标识、包名、架构、渠道及版本号，仅存手机本地，沿用每日清理和用户主动导出。
- 发布验证脚本改从 APK 独立读取 AppID、从客户端配置读取渠道，不再拿远端清单补成本机身份；适配现有独立取消信号到 Node fetch 的 AbortSignal。首次发布验证因此发现脚本旧适配不兼容，修正后完整通过；没有修改手机端以依赖浏览器取消接口。

参考：[Android Build 架构字段](https://developer.android.com/reference/android/os/Build)、[Native.js 属性读取及失败返回值](https://www.html5plus.org/doc/zh_cn/android.html)、[运行时 AppID 与调试基座](https://www.html5plus.org/doc/zh_cn/runtime.html)。
