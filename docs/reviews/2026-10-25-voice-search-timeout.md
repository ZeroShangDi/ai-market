# 语音联网偶发失败排查

日期：2026-10-25。用户表示“测试一下联网能力”曾失败，随后重新尝试恢复；原始调用没有分阶段诊断，不能断言与复现问题完全相同。

## 证据

- 真实 WebRTC 官网查询曾返回“联网查询没成功、返回不到可靠来源”，直接接口查询则成功，确认存在间歇失败。
- 公开新闻查询捕获 `stage=search error_type=TimeoutError elapsed_ms=45010 completed=False source_count=0`：语音插件在后台搜索完成前触发 45 秒总时限。
- 原临时语音验证只判断有足够长度的回复，失败文案也能通过；现改为检查实际官网域名并排除失败提示。发布时记录的成功域名仍有原始输出依据，但单次通过不证明稳定性。

## 修复与验证

- 搜索等待调整为 120 秒；工具清单声明 150 秒时限，为手机鉴权最多 20 秒保留余量。底座通用支持 1–180 秒工具时限，其他工具仍为 60 秒，没有新增搜索专属底座分支。
- 保留真实来源和完成回执校验；超时、授权异常分别明确提示。阶段日志只包含错误类型、白名单错误码、状态码、耗时与来源数量，不记录查询、回复或凭据。
- 语音自动测试 46 项，45 通过、1 项按配置跳过。原新闻问题修改后返回成功和 8 个真实来源。
- 重启 Mac 语音服务后，真实 WebRTC 官网查询返回 `www.cas.cn` 并口述来源，370 个有效音频帧、零警告，会话记录保存正常。无需重新打包手机。
- 尚不能排除搜索提供方临时失败、其他复杂查询超过两分钟或手机网络异常；本次未将所有偶发联网问题标为解决。

## 后续：公开搜索原话校验误拦截

- 用户再次反馈频繁听到“需要完整引用本轮用户原话”。本机服务日志发现 6 条 `voice_search_failed stage=user_request reason=quote_mismatch`，确认请求在搜索及手机授权之前被原话校验拒绝。日志未记录正文，无法判定每次具体是标点、空格、改写还是用户轮次变化。
- 原实现要求模型生成的 `user_quote` 与会话最后一条用户消息严格相等；只读搜索因此依赖模型再次复制转写。移除搜索工具的该参数，由插件直接检查可信会话中存在非空用户请求；仍只发送必要公开查询词，仍核验手机授权与来源完成回执。任务创建、续聊及审批答复继续使用原严格校验。

- 本机语音服务已重启加载，健康检查通过；本次未进行手机真实语音搜索验收。

## 后续：查询后连续追问无回复

- 补充技能并重启后仍复现沉默。最新一轮服务日志出现两次搜索 HTTP 429，随后六次模型 HTTP 422，另有识别失败；仅检查健康接口不能覆盖真实对话链路。
- 使用合成对话复现 Pipecat 异步结果：工具运行期间出现新用户轮次时，框架将最终结果追加为 `developer` 消息。DeepSeek 拒绝该角色，返回 422；消息留在上下文后，后续请求继续失败。原始格式测试返回 422，转换后的同一组消息返回 200。
- 模型适配层对 DeepSeek 启用 Pipecat 自带的消息角色兼容转换，只改变发往模型的消息副本。共享会话保留原始角色，工具结果不能成为 `user_turn()` 的用户原话或审批依据。其他模型供应商保持原有处理。
- 搜索 429 明确提示繁忙且未接收，不自动重复提交。识别端增加错误类型和状态码诊断，不记录音频、正文、凭据或请求响应体；一秒合成静音实测识别返回 200，不能据此断言此前识别失败的具体原因已解决。
