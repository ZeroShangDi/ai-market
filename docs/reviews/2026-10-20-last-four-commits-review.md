### 1. [P1] 播报被插话打断后，同一通知无法重播

- 位置：`apps/voice-service/voice_service/work_bridge.py:93`，关联第 34–37、70–71 行。
- 引入：`01038be5`，后续提交仍保留。
- 触发：后台结果开始播报，用户插话打断；手机端没有收到播放完成确认，随后重发相同通知 ID。
- 原因：开始播放前就把 ID 加入 `accepted`；插话只清除 `speaking_notice` 和历史，没有移除 `accepted` 或重新入队。重发进入 `receive()` 后直接被丢弃。
- 影响：同一语音会话内不能补播完整结果。手机等待 45 秒后可能回落到文字/桌宠；若没有可用回落入口，会持续超时重试。任务本身仍保存于 Work，不是任务丢失。
- 验证：用轻量帧替身执行实际 `WorkAnnouncements` 逻辑，开始播放→插话→重发后得到 `accepted=['work:1']`、`pending=[]`、`speaking_notice=None`。现有测试只验证打断时不确认收到，没有验证随后重播。
- 建议：区分播放中与已送达；完整播放后才记为已送达，打断后允许重试，并覆盖插话、取消、超时和重复确认。

### 2. [P2] 查询/思考动作没有服务端事件来源

- 位置：`apps/voice-service/voice_service/pipeline.py:54`，关联手机端 `src/modules/voice/index.ts:107` 和两套资源的 `scenes.json`。
- 引入：`a95a86f5` 删除旧查询代理时移除了查询前的 `thinking` 事件。
- 原因：现有语音状态处理只发送 listening/speaking；扫描服务端 Python 源码，没有 thinking/working 状态的发送者。客户端虽然支持映射，两套资源也配置了对应动作，但真实查询无法触发。
- 影响：语音查询或等待后台任务时，桌宠不会切换到配置的思考/工作动作；映射单测手动注入状态，因此仍然通过。
- 建议：在通用工具执行生命周期及插件任务状态之间补齐状态通知，明确提交中、后台执行、继续聊天和打断的优先级，避免将具体查询能力硬编码回语音底座。
- 验收：真实发起查询，观察任务提交和等待时的动作；插话、结束、失败后能恢复，后台工作不得覆盖正在说话的动作。

### 3. [P2] 已关闭会话可能通知为“已完成”，并引用旧结果

- 位置：`apps/call-phone-uni/src/services/voice-work.ts:73`。
- 引入：`01038be5`。
- 触发：一个会话有未读的成功历史结果，后来关闭会话。服务端列表保留 closed 会话，unread 仍按历史成功 result 判断。
- 原因：通知过滤不排除 closed；状态文案只判断 pending、failed、interrupted，其余统一为“已完成”；结果使用最后一条 assistant 消息，可能来自上一轮。
- 验证：执行实际通知器，输入 `status='closed'`、`unread=true` 和旧回复“上一轮结果”，实际输出为 `任务“旧任务”已完成。上一轮结果`。
- 建议：穷举状态；关闭应跳过或明确写“已关闭”。完成结果必须绑定成功轮次，不能把历史回复当作当前执行结果。

### 4. [P2] 应用角色资源会强制重新打开已关闭的桌宠

- 位置：`apps/call-phone-uni/src/App.vue:34`，特别是第 38 行。
- 引入：`01038be5`。
- 触发：用户关闭手机宠，只想给 App 内文字/语音选择角色，随后应用另一个资源包。
- 原因：回调读取了原 enabled 状态，但仅用于关闭旧桌宠；只要新资源存在就无条件调用 `setMobilePetEnabled(true)`。
- 影响：用户的关闭偏好被覆盖；无悬浮窗权限时还会进入权限设置。资源切换成功也可能因为桌宠显示失败被呈现为操作失败。
- 建议：将资源选择和桌宠开关解耦；仅在原本启用时刷新显示，保留原开关偏好。分别覆盖首次加载、关闭状态切换、启用状态切换、删除当前资源。
