## 核心问题：5 项，建议优先修复

### 1. [P1] 电话插件注册在错误的配置层级

- 位置：[manifest.json](../../apps/call-phone-uni/src/manifest.json:42)。
- 现状：`app-plus.distribute.nativePlugins.leven-call`；正确层级是 `app-plus.nativePlugins.leven-call`，旧版也使用正确层级。
- 证据：本轮实际生成的 `dist/build/app/manifest.json` 中，`plus.nativePlugins` 为空，插件仍在 `plus.distribute.nativePlugins`。所以 App 资源编译成功并未验证有效插件注册。
- 影响：按当前工程配置制作自定义基座/云打包，不能依赖该节点加入电话插件。外部预先装好插件的基座可能掩盖此问题，但无法证明当前正式包配置正确。
- 建议：把现有插件声明移到正确层级，保留已有插件 ID 和应用身份，再检查新生成清单并重建基座。无需另写插件。
- 依据：[DCloud 原生插件格式说明](https://ask.dcloud.net.cn/article/id-35414__page-4)、[当前 leven-call 插件页](https://ext.dcloud.net.cn/plugin?id=16275)。

### 2. [P1] 同样是 App 前台，离开客户页就停止接收派发与心跳

- 位置：[客户页](../../apps/call-phone-uni/src/pages/customers/index.vue:323)、[App.vue](../../apps/call-phone-uni/src/App.vue:1)。
- 触发：配对后留在“我的”、转到工作台或客户详情；这些页面没有派发轮询，客户页隐藏时会清除计时器。
- 证据：执行实际 Vue 页面中的 setup/onShow 代码，使用服务替身和计时器探针：客户页注册 `15000ms` 轮询，“我的”和工作台均注册 0 个轮询。配对成功仅发送一次心跳。
- 影响：新派发没有入口提示；后端设备列表以最后心跳后 2 分钟判断离线，手机仍在使用时 PC 也会失去在线设备选项。
- 服务端依据：[DevicePairingController](../../apps/ruoyi-vue-pro/yudao-module-callphone/src/main/java/cn/iocoder/yudao/module/callphone/controller/admin/outbound/DevicePairingController.java:47)。
- 建议：复用现有 API，在 App 前台生命周期中统一维护单一心跳/派发服务，各页共享通知和接受入口；切换页面不停止前台服务。后台保活属于另一项能力，不应把它混入本修复。

### 3. [P1] 电话未结束也可回填完成，造成 0 秒记录和录音遗漏

- 位置：[结果弹层](../../apps/call-phone-uni/src/components/CallResultSheet.vue:28)、[completeCall](../../apps/call-phone-uni/src/services/calls.ts:130)。
- 触发：拨号成功后，在系统电话仍进行时返回 App，选择“已接通”并保存。弹层只要求已选结果，没有要求通话已结束，也没有人工确认结束步骤。
- 证据：对实际通话服务模块提供拨号/服务替身，在未发送任何 native ended 事件时完成回填，得到 `outcome=synced`、提交时长 `0`、通话锁 `false`。
- 影响：服务端提前结束通话；页内 activeCall 随 saved 清空，后续挂断回调被忽略，实际时长/录音无法归入该记录；同时允许开始另一通话。
- 建议：成功发起拨号时保留“通话进行中”状态，收到结束事件后才允许正常回填。无法可靠收到回调时提供明确的人工结束确认，继续保留拨号超时的核对入口。

### 4. [P1] 重启/重新登录配对后，同一手机无法读取旧身份产生的录音

- 位置：[HTTP 凭据容器](../../apps/call-phone-uni/src/api/http.ts:4)、[配对认领](../../apps/ruoyi-vue-pro/yudao-module-callphone/src/main/java/cn/iocoder/yudao/module/callphone/controller/app/outbound/CallPhoneMobileController.java:96)、[录音权限](../../apps/ruoyi-vue-pro/yudao-module-callphone/src/main/java/cn/iocoder/yudao/module/callphone/controller/mobile/CallPhoneMobileV1AdapterController.java:337)。
- 代码链路：设备凭据只在进程内存；重启或清理登录态会丢失凭据；每次认领配对码新建 deviceId；播放旧录音要求通话和录音的 deviceId 都等于当前 deviceId。
- 影响：详情仍会显示旧录音为 ready，但同一手机重新配对后请求 recording-access 会被拒绝；PC 留下多个旧配对设备记录。此结论来自实际代码条件核对，尚未在真实数据库复现。
- 建议：用系统安全存储保持稳定设备身份，并支持受控的登录/凭据恢复、轮换和撤销。若产品希望同账户其他设备可听历史录音，需要单独设计服务端授权，不能直接删除设备归属校验。

### 5. [P1] 登录状态清理不能隔离正在执行的通话请求

- 位置：[completeCall 的完成与失败回调](../../apps/call-phone-uni/src/services/calls.ts:169)、[clearCallState](../../apps/call-phone-uni/src/services/calls.ts:214)、[session.login](../../apps/call-phone-uni/src/services/session.ts:23)。
- 触发：通话回填请求仍在等待；认证恢复/重新登录触发 clearCallState；新会话开始另一通话；旧请求随后失败。
- 证据：执行实际服务模块，按上述顺序模拟延迟失败。新通话 ID 为 `22`，但旧请求返回后 `hasUnfinishedCall=false`，并重新插入 1 条旧待同步任务。
- 影响：旧任务污染新会话队列，旧回调解除新通话锁；新账户可能被无权重试的旧任务阻塞。HTTP request 层虽有 sessionVersion 校验，通话服务 catch/finally 的副作用没有同样隔离。
- 建议：给通话、重试和创建操作绑定会话代次/账户及当前通话 ID；旧代次返回不得改动新队列、通话锁或页面。clearCallState 同时使旧操作失效，不能只清空当前数组。

## 其余缺口与改进项

### 旧版能力对照与范围决定

[工作台](../../apps/call-phone-uni/src/pages/index/index.vue:1)只有标题、账户入口和底栏，仍无业务内容。以下旧版能力未在新版 uni 中找到同等入口/实现：

| 旧版已有能力 | 新版当前情况 | 本次决定 |
|---|---|---|
| 手机按日期查看呼入/呼出次数、时长、有效率报表 | 没有移动报表页或 API 接入 | 用户确认不做，不列入修复 |
| 按日期浏览、播放本机录音文件 | 只有某客户最近通话的服务端录音播放，没有本机录音库 | 保留客户沟通记录播放入口，修复播放链路，不新增本机录音库 |
| 来电记录处理 | native 适配明确过滤来电，不写入新客户通话；旧版会处理来电 | 待明确需求；本轮验证来电干扰不会破坏正在进行的外呼 |
| 系统拨号界面选择卡 1/卡 2 | 旧版注释明确为此改用 `plus.device.dial`；新版改用 `module.callPhone`，没有 SIM 选择参数/入口，是否满足需求需双卡真机验证 | 先验证兼容性；如有缺陷，优先复用已有适配方法修复 |
| 应用自动检查更新 | 旧版引入 upgrade-center；新版没有更新检查入口 | 用户确认按通用模块实现，见独立方案 |
| 旧 uniCloud 登录/任务/通话数据 | 新版使用 Yudao 员工账号、客户侧接口；未找到旧用户/数据迁移实现，保持 AppID 不会自动迁移账户与数据 | 暂不承诺迁移，另行明确 |

上述范围变化不能一概算实现 bug，也不能声称“旧版所有功能已升级保留”。后续按已确认范围修复，不重新加入手机报表或独立本机录音库。

### [P2] 权限诊断可查看状态，缺少配置引导入口

[原生适配](../../apps/call-phone-uni/src/native/phone.ts:147)已有 openRecordingSettings/openFilePermissionSettings，但[诊断面板](../../apps/call-phone-uni/src/pages/mine/index.vue:129)没有调用按钮。旧版会在未开启时提供“文件权限”和“通话录音权限”跳转。插件读取的是手机系统产生的录音，不代表应用装上插件就自动开启录音。

建议复用已封装的方法显示未开启状态的操作按钮，返回 App 后重新检查；给权限检查增加超时和异常反馈。目前新 manifest 的权限是旧版的一部分，不能直接把旧版全部权限复制回来，也没有 APK 可检查最终合并的 Android 权限声明。

### [P2] 离线结果和录音恢复能力不完整

- [pending](../../apps/call-phone-uni/src/services/calls.ts:32)只在内存；杀进程会丢失未同步结果/上传任务。这是已记录的限制，不是持久离线支持。
- 自动重试只在 App onShow 和用户手工“重试同步”触发，未订阅恢复联网；应用保持前台时网络恢复不会必然自动重试。
- completeCall 捕获所有异常后统一排队，drain 在第一个失败任务停止；无权、参数错误、设备撤销等永久失败也会长期占据队首。signOut 又要求先清空 pending，缺少错误原因/修正/受控处置入口。
- [uploadRecording/downloadRecording](../../apps/call-phone-uni/src/api/http.ts:212)直接使用 uni 文件 API，没有 JSON request 已实现的令牌刷新与会话隔离。对实际上传模块模拟 401，得到 AUTH_REQUIRED，刷新请求次数为 0；必须靠其他 JSON 请求先刷新或再次登录才能恢复。下载还把所有非 2xx 错误统一展示为无录音/无权限。
- pendingCompletionCount 是普通函数/数组，不是响应式状态；后台重试完成后“我的”中的数量未必立即更新。

建议统一 JSON 和文件传输的会话/刷新规则，按暂时失败、需重新授权、永久失败分类，提供可观察的恢复状态；采用系统安全存储持久化必要待同步事件，并以原幂等键恢复。不得用明文本地存储代替安全队列。
