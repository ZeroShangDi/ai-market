# 待办 issue：多应用入口的 uni 与 H5 应用划分及管理边界

日期：2026-10-14

状态：已记录讨论结论，待后续规划落实，暂不实施。

## 背景与目标

移动端后续作为多应用入口。大部分普通业务应用由各自模块独立开发、部署，通过 H5 嵌入接入，以减少安装包发布；少数依赖移动端特殊能力的应用继续在 uni 项目中实现。

其他会话正在规划多应用入口，具体目录命名及入口交互与该规划对齐。

## 已确定的方案

### 应用划分

- uni 应用：涉及移动端系统权限或特殊能力，例如电话、录音、蓝牙、悬浮窗、后台运行等，直接在 uni 项目中实现。涉及原生能力或权限声明的变更，通过安装包版本更新发布。
- H5 应用：不依赖移动端特殊能力的普通业务应用，通过网址嵌入。页面和业务代码保留在各自模块，不放入应用框架；新增入口和发布 H5 页面通常无需更新安装包。
- 当前不建设通用 H5 原生能力桥接、动态权限声明或任意 H5 后台执行体系。
- 后续 H5 应用若需要移动端特殊能力，优先调整为 uni 应用。

### uni 应用的目录约束

- 每个 uni 应用的业务实现限定在自己的独立目录中，收拢页面、组件、状态、权限检查和原生适配。
- 框架保持轻量，负责应用注册、入口及必要的生命周期调度。
- 业务逻辑不散落在框架中；应用向宿主暴露必要的初始化、恢复和停止方法。
- 必须在宿主统一配置的页面路由、原生插件、权限和服务声明等保留必要的集中配置，具体业务实现仍归属应用目录。
- 目录隔离是代码组织边界，不是操作系统权限或进程隔离；同一安装包的系统权限仍属于宿主。

### 页面切换与后台任务

- 离开应用页面，不应丢失仍在执行的任务或未保存数据。
- 电话监听、电脑派发接收等不能依赖拨号页面是否打开，应归属拨号应用的服务逻辑，由宿主按需调用其生命周期方法。
- 目录收拢不等于具备后台常驻能力；确实需要后台执行的应用仍需根据平台限制实现相应原生机制和恢复策略。
- 未完成通话、待保存结果和待同步结果需持久化，并提供全局发现及返回处理入口。

## 与已有拨号迁移 issue 的关系

已有记录：[拨号应用迁移后的全局状态处理](./mobile-call-migration-issue.md)。

该记录中的电脑派发监听、通话状态、跨应用切换、后台返回和重启恢复问题继续保留。按本次结论，拨号作为 uni 应用实现，业务逻辑收拢在拨号应用目录，宿主仅承担必要调度与全局入口职责。本 issue 不替代拨号迁移问题的单独设计。

## 后续验收方向

- [ ] 多应用规划明确区分 uni 应用和 H5 应用，并遵循上述接入边界。
- [ ] uni 应用拥有明确的独立目录及必要的生命周期接口。
- [ ] H5 页面在所属模块独立部署，新增普通 H5 应用无需修改宿主业务代码或发布安装包。
- [ ] 框架仅保留必要的注册、路由、平台配置及调度，避免混入应用业务实现。
- [ ] 拨号跨页面切换不漏接派发、不丢失未保存结果，并验证后台返回及重启后的恢复。
