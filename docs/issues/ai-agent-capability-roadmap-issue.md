### 0.2 待处理 issue：Work 结束后无法查看执行历史（2026-10-16）

- 状态：已记录，待排查；本次仅登记问题，未实施修复。
- 用户反馈：任务模式执行结束后，无法再查看此前的执行历史。
- 影响：普通用户对过程细节的需求较低，但测试期间需要回看执行步骤、工具调用及结果、错误和交互记录，以核对实际行为并定位问题。
- 期望：任务结束后仍可按需展开查看该轮执行历史；退出会话再进入后也能回看。保持默认界面简洁，不增加常驻过程说明。
- 待排查：区分前端隐藏/清空、历史事件未加载或回放不完整、后端记录缺失等情况；尚未确认根因，也不将界面不可见直接判定为记录已丢失。优先复用现有 Work 事件持久化与回放能力。
- 验收：完成、失败或打断后均能查看对应轮次的执行记录；重新进入会话及后续继续任务后，之前轮次的记录仍可定位，且不会与新一轮混淆。查看历史不得触发任务重新执行。

| C14 | 资料维护 / 销售 | 根据我提供的资料更新客户字段、标签和阶段 | 变更前后预览、保存回执 | customer/save、tags-batch、字段/阶段 options；A。阶段推进依据由用户或已核对事实提供 |
| C15 | 下一步 / 销售、客服 | 给这位客户安排明天下午回访，把原来那条改期 | 新建/改期后的待办和明确截止时间 | follow-up-task/page/save；A。改期需定位具体待办，不重复新建 |
| C16 | 待办处理 / 销售、客服 | 这项回访已经做完了，完成它；不再需要的取消 | 完成/取消回执与记录状态 | follow-up-task/complete/cancel；A。系统标记完成不代替证明实际服务已完成 |
| C17 | 通话复盘 / 销售 | 按这次沟通内容整理需求、异议、结论和下一步 | 待复核总结和来源 | 通话总结人工 save/review；B。现页面 AI 生成禁用，需接生成来源与写回；仅有录音时还需转写能力 |
| C18 | 建议执行 / 销售、主管 | 把已复核总结中的下一步整理成待办，确认后创建 | 建议列表、采纳/驳回记录、待办 ID | 跟进建议 prepare/update/adopt/dismiss、人工复核；A。采用已有总结提取与幂等采纳，不冒称现有 AI 生成 |
| C19 | 交接 / 主管 | 整理这些客户的交接清单，确认后转给指定同事 | 客户状态、未完事项、负责人变更回执 | customer/assign-batch、线索改派；B。客户改负责人不代表待办、通话、企微关系自动转移，分别列出缺口 |
| C20 | 分层 / 客户运营 | 按已有阶段、标签和跟进情况整理回访人群 | 可追溯名单、规则、数据截止时间 | 客户列表、批量标签、跟进；B。需补筛选/聚合；“未更新资料”不等于“长期未联系” |
| C21 | 企微资料 / 客户运营 | 同步指定成员的企微客户和群，汇总失败项 | 同步任务 ID、进度、成功/失败计数 | 企微客户、客户群与同步 job；B。依赖真实企微授权；不假设企微客户已与 cp_customer 自动匹配 |
| C22 | 运营活动 / 客户运营、审核人 | 为这批客户准备回访活动，估算人群并提交审核 | 草稿、人群快照、审批状态 | 客户运营 save/estimate/submit/withdraw 及审核流程；B。真实企微发送未接入，审批通过不等于已经触达 |
| C23 | 风险处理 / 销售、客服 | 检查我的逾期跟进和长期未更新客户，整理处置计划 | 预警清单、处置建议、确认后的处置记录 | 风险预警 scan/page/resolve；A。当前两种内置规则且限本人，不能直接给出全团队扫描结果 |
| C24 | 服务质检 / 客服、质检 | 检查这些已结束通话的服务流程，列出问题供我复核 | 五项检查草稿、证据、复核后评分及整改建议 | 服务质检 available-calls/page/save/recording；B。现有本人范围，独立质检员跨员工访问及自动音频分析需补 |
| C25 | 工作准备 / 销售、客服 | 根据已发布话术和产品资料，准备客户异议回应 | 引用版本/来源的回答草案 | 话术版本、知识库；B。话术读取可复用，知识库面向 Work 的检索及部门范围过滤待接通 |
| C26 | 经营复盘 / 主管 | 汇总本周团队获客、转化、通话和跟进情况，输出周报 | 标明口径与缺失项的统计表和周报文件 | 渠道分析、线索转化、通话 summary、跟进；B。部分接口仍限本人，须补团队汇总范围，不能声称已有收入指标 |
| C27 | 退出/纠错 / 销售、主管 | 把确认无效或重复的线索归档，误归档的恢复 | 原因、目标关联、归档/恢复回执 | 线索 archive/restore、客户 archive；A。线索恢复已有接口；客户恢复未在当前接口清单中提供，不承诺同等可恢复 |
| C28 | 业务配置 / 管理员 | 检查团队开展客户工作缺哪些字段、阶段、权限或设备配置 | 差距清单和逐项配置方案 | 成员、团队角色、数据权限、客户字段、阶段、设备、扩展服务；B。先做检查，变更按已有动作权限落实 |
| C29 | 成交与回款 / 销售、财务 | 整理报价、合同、订单、应收和回款，提醒到期款项 | 商务记录、应收对账与回款状态 | C。模板 CRM 有相关源码，但未与当前客户域接通；不能用客户阶段模拟合同或收款事实 |
| C30 | 交付与续费 / 客户成功、客服 | 跟踪交付、服务工单、到期续费和再次购买机会 | 交付/工单/续费计划与业务回执 | C。现有跟进事项只能承载人工安排，订单履约、服务期限、工单状态及续费依据需要业务接入 |

#### 从任务归并工具与系统连接

先建设一个受管理的 Call Phone 业务连接，按职责提供工具组，复用原有 Java 业务用例。下表是候选工具边界，不是已经存在的 MCP 名称；不为每个任务复制一套服务，也不一次暴露所有后台接口。

| 工具组 | 支撑任务 | 先接的业务能力 |
| --- | --- | --- |
| 客户与跟进读取 | C08、C09、C13、C20、C26 | 查询/定位客户、详情、可见字段与阶段、跟进事项、通话与可用关联历史 |
| 客户与待办写入 | C04、C14–C16、C19、C27 | 导入、保存、标签、改负责人、归档；待办创建/修改/完成/取消 |
| 线索流转 | C03、C05–C08、C11、C12、C19、C27 | 入池、领取、规则预览/应用、分配/回收、跟进、转客户、归档/恢复和回执查询 |
| 通话执行与复盘 | C10、C17、C18、C24 | 在线设备、派发/查询/取消、通话详情、总结草稿/复核、建议采纳、质检 |
| 获客与分析 | C01、C02、C26 | 渠道/活码/链接、现有统计；缺失的团队汇总与海报产物另补 |
| 风险与运营 | C20–C24 | 风险扫描/处置、企微同步及 job 查询、活动草稿/估算/审批 |
| 知识与组织配置 | C25、C28 | 已发布话术、受权限约束的知识检索、成员选项与必要配置读取 |

系统连接顺序：先接项目自己的 Call Phone 后台；企微能力仍通过已有后台适配器及其授权配置调用，不在 Agent 中复制一套企微凭据；合同/回款/交付等确定真实业务系统与客户 ID 关联后再接。文件生成继续复用现有 Work 工作区和产物能力。

实施时注意已有代码并非所有逻辑都在 Service：例如客户 Controller 内仍有查询/保存逻辑，若新入口需要共用，应按项目规矩增量提取公共用例，保留 PC 行为与权限校验，避免复制读写 Mapper 的另一套实现。

每个工具的最小契约：实际操作者身份和租户由可信服务端传入；对象 ID、筛选范围和分页明确；结果包含业务 ID、状态、数据时间、失败原因及可核对回执。写入沿用现有幂等/版本能力，缺失的逐项补齐；未知执行结果先读回核验。工具入口必须保留页面对应的动作权限、行/字段范围，不能用高权限服务账号把权限放大。只读、草稿写入、业务状态变化、外部触达分别登记实际影响，不因为用了 MCP 就全部要求额外确认。

#### 实施顺序与完成标准

1. **第一批：销售每天可用的客户工作闭环。** C13 客户简报 → C09 今日跟进清单 → C15/C16 待办安排与处理 → C14 客户资料维护。先让客户、通话、待办在授权范围内能被正确找到；输出文件复用现有能力。首个验证任务：“整理我今天到期和逾期的客户跟进，说明优先顺序；按我确认的时间调整选定待办，返回实际变更结果。”
2. **第二批：主管与销售的线索流转。** C03、C05–C07、C11、C12、C19、C27；复用已有分配规则和回收任务。交接必须显式处理客户、线索、待办等对象的归属差异。
3. **第三批：联系、复盘与知识辅助。** C08、C10、C17、C18、C23、C25；先用真实文字/已核对内容形成总结，音频转写另行验证。
4. **第四批：市场、客户运营和团队管理。** C01、C02、C20–C22、C24、C26、C28；在各接口团队权限补齐、真实企微授权和关联验证后实施。
5. **后续业务扩展。** C29、C30 先补业务模型或外部系统连接，再承诺成交、回款、交付和续费闭环。

顺序是基于当前代码基础的实施建议，不代表全部任务已获上线或真实业务执行授权。当前先确认任务口径并完成第一批具体契约，再进入工具实现。

每批都用本人/同部门/无权用户的合成数据验证：完整分页、事实来源、时间口径、授权范围、写入后读回、幂等重试及失败/中断后的真实状态。跨接口身份和数据范围不一致时应明确缺失，不用不完整数据输出“全量”结论。0.2 的执行历史问题保留为测试可观测性待办，业务验收需要能追溯工具调用和回执，不将过程不可见视为操作未执行。

#### 最后沉淀技能

工具在真实任务中跑通并复核后，再提炼“每日客户跟进”“线索分配与交接”“通话复盘与下一步”“渠道与团队周报”“客户回访活动”“风险处置与服务质检”等技能。每项技能明确触发场景、必要资料、事实来源、工作步骤、检查点、输出模板、失败与恢复方式；技能复用同一套工具，不自行承载业务权限或绕过后台规则。当前仅列候选，不提前创建空技能。

## 1. 最新讨论基线

本文件统一维护 AI 能力需求、讨论结论、待决问题与后续工作，不按文件、语音、连接器等另建平行计划。历史实现、协议与验收记录通过链接保留。

用户本轮明确：

- 基础聊天与联网问答初步验收，本轮只讨论能力，不继续围绕安装打包和真机验收排计划。
- 当前资料任务的形态完全不符合需要，可能重做；此前技术闭环通过不等于产品形态获得认可。
- 核心投入转向 Work：用户用自然语言交办，AI 结合资源、技能、MCP、连接器等完成系统操作与工作闭环，用户在核心检查点确认。
- 目标是秘书型助手，覆盖沟通、资料整理、系统操作和 AI 资源生成，并逐步代替原本必须坐在电脑前完成的工作。
- 有成熟、可接入的能力优先接入；成熟但无开放接入方式的能力，先评估官方合作/API、受支持的自动化及自建成本，不默认全部自研。
- 保留外部对话框架，输入框左下增加“+”作为统一资源入口；特殊内容采用统一流式展示协议，由独立渲染层承接。
- Work 沟通采用简短工作汇报；支持后续沟通工具事件触发的自动回复、任务识别与自动执行，必要时询问或确认。
- 资料不足等导致的停滞必须进入程序中的持久状态，不能只留下一句聊天说明。
- 后续补充明确：先搭通用基础设施，再逐步叠加功能；不能把选择首个业务流程作为设计地基的前置条件。CSV 导入线索、分配本人客户拨号任务、整理今日需联系客户是检验架子的例子，不是三个固定流程的开发排期。
- 前期实验对象为本项目自己的 PC 前后端，通过自有后端提供的能力执行；输入可以是自然语言，也可以是自然语言加文件。暂不以外部沟通软件接入或控制个人桌面作为底座建设的前提。

以下“建议”和“待讨论”保留能力讨论背景；当前已实施的范围、证据与限制统一以第 0 节为准。

## 2. Chat 与 Work 的区分

官方 ChatGPT 文档将 Chat 定位为问答与往返讨论，将 Work 定位为委托多步工作并取得可审阅结果。两种模式都可能使用工具；不能简单以有没有联网或插件来划分。官方未公开完整内部实现，下面是本项目的产品与后端设计建议。

| 维度 | Chat | Work |
|---|---|---|
| 用户意图 | 了解、讨论、比较、获取建议 | 交办一个结果，或持续负责一个目标 |
| 完成判断 | 本轮回答满足问题 | 产物与实际操作结果达到完成条件，并有证据 |
| 资源与工具 | 可检索、读材料并辅助回答 | 在授权范围内组织技能、工具、应用与执行环境 |
| 持续性 | 以对话轮次为主 | 任务与运行记录持久化，可等待、补充、恢复、跟进 |
| 用户参与 | 继续提问或改写 | 补信息、作决定、确认关键操作、查看结果 |
| 汇报风格 | 按问题需要展开 | 已完成、需你决定、阻塞、下一步，详细过程按需展开 |

建议沿用同一对话外壳，明确 Chat/Work 模式；Chat 可转为 Work，并带入选定上下文。切换模式不自动扩大权限、不默认把所有历史材料交给工具。Work 中也可继续讨论和调整方向。最终采用会话级模式还是单次交办级模式待讨论。

## 3. “+”资源入口与后端能力映射

“+”是选择材料、方法、系统和工作范围的统一入口。界面可按资料、能力、应用/连接、目标/自动化、执行设备分组，选中后显示可移除的资源标签；不要求普通用户理解 MCP 等技术名词。现有授权目录内，AI 应能按需发现资源和能力，避免每次执行都要求用户逐个勾选；“+”支持显式指定、限定和覆盖默认选择。

| 入口项 | 后端实际对象/能力 | 需要明确的边界 |
|---|---|---|
| 文件 | 资源引用、版本、解析/转换/编辑工具、产物存储 | 上传成功不等于已支持读取或修改；记录权限、格式与来源 |
| 文件夹 | 工作区挂载或目录授权、枚举/搜索/读取/受控写入 | 手机目录、本机电脑目录、云盘目录、云端工作区必须区分；上传文件夹快照不等于持续访问原目录 |
| 网页/链接 | 来源引用、搜索/浏览/提取工具 | 需要登录的网站依赖相应执行环境与授权 |
| 技能 Skill | 有版本的工作方法、模板、脚本与依赖声明，按需加载 | 方法本身不会赋予权限，也不自动提供缺失的程序与工具 |
| MCP | MCP 服务连接与其暴露的 tools/resources/prompts 的适配 | 连接协议不等于账号授权或运行环境，服务可在本地或远端 |
| 连接器 | 账号连接、权限范围、凭据生命周期、API/事件适配 | 通过 MCP 或直接 API 暴露均可；事件订阅能力需另行支持 |
| 插件 | 可安装版本包，组合技能、工具/MCP、配置及可选展示扩展 | 安装、启用、绑定账号、授予操作权限是不同状态 |
| 应用 | 可操作系统的能力清单与适配器 | 有应用入口不等于 AI 可控制；可能采用 API、浏览器或桌面自动化 |
| 专家/助手配置 | 组合技能、允许的工具、输出要求与默认策略 | 复用同一工作运行时，不复制独立任务系统 |
| 目标 Goal | 持久目标、完成条件、约束、预算、子任务与跟进策略 | 目标可跨多次运行，不等同一次提示或 SDK 最大轮数 |
| 自动化/自动接单 | 事件/定时触发规则、处理范围、运行身份与授权策略 | 自动触发不自动授予回复、发送或修改权限 |
| 执行设备/空间 | 已注册 Worker、能力/在线状态、授权目录与环境 | 选择哪台电脑或云端执行，不能把手机路径发给服务器假设可读 |

建议任务保存类型化的资源引用、选定版本、授权引用及执行位置；凭据留在受控凭据管理与工具端，不把密钥拼进提示词。能力目录区分已安装、已配置、已连接、已授权和当前可用，并处理缺依赖、断线、授权过期。

## 4. Work 执行闭环

建议的运行链路：接单 → 明确结果和边界 → 收集资源 → 形成必要计划 → 执行 → 检查结果 → 询问/决策/确认 → 继续 → 交付与流转 → 跟进。

| 基础能力 | 平台需要保存或提供的东西 |
|---|---|
| 接单与目标 | 请求来源、交办人/运行身份、上下文、期望结果、完成条件、关联目标 |
| 计划与执行 | 步骤、依赖、资源、技能/工具版本、执行环境、可调整的任务计划 |
| 检查点 | 已核验阶段、产物版本、外部操作回执、恢复位置；是否回滚另行判断 |
| 决策点 | 需要选择的方案、依据、影响、选择人与结论；不记录模型私有思维链 |
| 提问 | 缺什么、为什么需要、问题和选项、答复及其对应任务/步骤 |
| 操作确认 | 具体对象、收件人/目标、内容或改动、影响范围、授权有效期及绑定版本 |
| 结果检查 | 文件可读与内容核验、修改前后差异、外部系统读回/回执，区分已生成与已实际生效 |
| 产出与流转 | 原件/解析件/派生件、预览、下载、版本、来源、归属、传给下游任务或外部系统的引用 |
| 操作日志 | 谁因何任务在何环境调用何工具、结果/失败、授权、确认、外部回执与关联事件 |
| 异常与恢复 | 超时、离线、权限缺失、信息不足、执行失败、取消与副作用核对，避免不确定写入盲目重试 |
| 进度与汇报 | 简短里程碑、待确认事项、阻塞、结果与下一步；完整细节可展开 |

检查点表示可核对/恢复的阶段，不承诺所有外部操作都能撤销。高危判定与强制确认由平台和执行端策略落实，不能只依靠模型判断或工具自报的风险注解。可预授权低风险、范围明确的动作；对外发送、删除/覆盖、批量操作、权限变更、财务相关等按实际对象和策略决定是否二次确认。

确认绑定不可变的操作参数与版本；修改对象、收件人或内容后旧确认失效。提交时重新校验权限、当前状态与确认范围，使用幂等键和回执；重复消息/确认不得重复产生副作用。浏览器/桌面路径也需要可实施的提交前检查点，不能只在提示词中要求“请先确认”。

## 5. 任务等待、阻塞与继续

建议持久化的任务状态包括：排队、执行中、等待补充信息、等待确认、等待外部依赖、已暂停、已完成、失败、已取消。步骤级另记录具体状态；部分步骤成功不应丢失。

阻塞记录至少含：原因类型、缺少的字段/资源/权限或离线设备、需谁处理、关联问题/确认、创建时间、已完成步骤、继续条件、下次检查或截止时间、提醒/升级策略和恢复上下文引用。

用户答复、授权恢复、设备上线、外部事件到达或明确重试后，重新检查条件并继续。等待中的任务不能占用一个永不结束的模型请求；平台状态独立于模型进程与 SDK 会话。重启/重连的恢复方式、执行上下文保存与副作用核对需要实际验证，不把当前原型的重启失败处理称为断点续跑。

## 6. 文件与生成资源能力

基础覆盖目标为 PPT、PDF、Word、Excel、CSV、TXT、MD。现代 Office 格式 `.pptx/.docx/.xlsx` 与旧 `.ppt/.doc/.xls` 的兼容/转换路径需分别定义；PDF 区分文本型和扫描型。

每种格式分别定义：读/提取、检索分析、生成、修改、保真/公式等语义验证、预览、下载与版本流转。“支持上传”不能代替这些能力已实现。文件解析与转换在后端受控环境完成，移动端通过统一资源卡与预览查看，复杂编辑/原生打开按场景选择。

跨资源能力还包括：全文检索、去重、命名归档、版本比较、引用来源、模板/品牌规范、批量转换、质量校验、产物交接，以及资料更新后识别过期结果。

## 7. 统一流式事件与特殊展示层（建议草案）

外部对话框架保留，内部增加独立的事件接收、任务/内容状态管理和组件注册层。采用版本化 JSON 事件，通过 SSE 等传输；事件先形成平台状态与可回放记录，再投影为前端展示，不能用渲染结果作为任务真实状态。

一个示意事件：

```json
{
  "protocol_version": "1",
  "event_id": "evt_123",
  "conversation_id": "conversation_1",
  "task_id": "task_1",
  "run_id": "run_1",
  "sequence": 12,
  "type": "ui.block.upsert",
  "block": {
    "id": "block_1",
    "component": "file_result",
    "version": "1",
    "revision": 2,
    "props": { "resource_id": "resource_1", "title": "会议纪要.docx" }
  }

```

- 生命周期事件与 UI 投影共用统一事件信封，但区分 task/step/tool/resource/interaction/ui 等语义。SDK 原始输出由适配器转换，模型不直接决定权威的完成/授权状态。
- 一个任务可多次运行；sequence 建议按 run 排序，事件 ID 去重，组件 ID/版本/修订控制覆盖。每个订阅范围有独立恢复游标，不把多个任务的 sequence 混为一个全局序列。
- 组件支持创建、完整更新、声明过字段的文本增量、结束和错误等动作；文本增量独立传输，结构化 props 用完整有效 JSON 更新，避免解析尚未闭合的 JSON。
- 前端注册表声明组件名、schema、版本、展示模式及支持的用户操作；新组件不改核心聊天逻辑。协议未知或版本不支持时提供摘要/资源链接降级，不静默丢弃。
- 历史快照与实时事件使用同一展示模型；断线重放不重复追加、展示或执行。用户动作通过独立命令接口携带 interaction_id、绑定版本与幂等键，由后端重新校验。
- 普通文字、工具进度、提问、确认、阻塞、结果与产物均能穿插在一条时间线上；运行日志默认折叠，不把长日志当工作汇报。
- 模型不能下发任意组件代码到宿主执行；固定组件由受控注册表提供。生成 HTML/React 等交互产物如后续引入，使用隔离预览与受限桥接，和有权提交业务操作的确认组件分开。

建议优先采用明确 API/连接器与可验证回执；网页工作使用浏览器自动化；只有必须操作原生程序或没有适合接口时使用桌面自动化。解析、转换、计算与生成可在受控文件/代码环境执行。MCP/插件可以封装这些路径，但不会自动让远程进程拥有用户电脑的文件和窗口。

## 10. 部署方式与“操作哪台电脑”分别决定

| 决策 | 选择 | 影响 |
|---|---|---|
| 平台部署 | 统一托管 / 私有化 / 混合 | 任务服务、数据/事件存储、连接器与管理边界 |
| 执行位置 | 云端 Worker / 客户内网 Worker / 用户个人电脑 Worker | 可访问的文件、网络、账号会话、程序及在线条件 |
| 模型位置 | 外部模型 API / 客户允许的模型服务 | 数据出域、能力、成本与运维；私有化平台不自动等于模型也在本地 |

这些是独立轴：统一托管平台可以调度个人电脑；私有化平台也可以调度内网服务器或用户电脑。纯 API 沟通/业务操作未必需要云电脑，有桌面 UI 依赖时才需要相应桌面环境。

建议先保持平台任务服务与 Worker 的明确边界，选择一个首发部署组合实测，不同时实现所有组合。手机作为交办、观察与确认入口；运行本机步骤需要对应电脑上的授权执行端在线。离线任务记为等待设备/资源，并可执行不依赖它的步骤；不能承诺云端可无缝接管离线电脑的会话。

需要讨论：首批操作的软件与设备、是否允许上传/缓存本地材料、个人/团队账号边界、运行身份、设备绑定/撤销、桌面会话可用条件、凭据与任务存储归属。

## 11. 自动接单与沟通闭环

建议链路：连接器事件或定时检查 → 去重/过滤 → 识别消息意图与可信来源 → 关联已有目标/任务 → 检索允许使用的资源与技能 → 形成/推进任务 → 需要时询问或确认 → 核验结果 → 回复/汇报并记录外部回执。

先定义规则：接哪些账号/频道/人、什么请求可自动回复、哪些任务可自动做、允许的对象/数据范围、何时必须确认、运行时间与预算、失败/超时交给谁、如何暂停全部自动化。

必须区分：收到消息、消息内容构成请求、请求人具有交办资格、系统拥有执行权限、可否自动对外发送。连接器里收到的任意文本不自动视作用户授权；邮件/网页/附件中的指令属于待处理内容，不能借此扩大权限。

自动回复、创建任务和发送正式结果应分开记录。处理重复事件、消息编辑/撤回、任务已存在、自己发出的消息再次触发、跨机器人循环、限流、取消与人工接管，防止重复回复和重复工作。对结果不确定的外部写入先核对回执，不自动换新请求重试。

工作汇报建议固定呈现：已完成、产出、需你决定、当前阻塞、下一步。只在有意义的进展、需要答复/确认、完成或失败时打扰；自动接单不等于不断发送状态消息。

## 14. 基础设施建设顺序与功能扩展方式（本轮建议，待讨论）

讨论顺序调整为：定义平台对象与边界 → 建立能力接入和执行契约 → 建立持久运行与人机交互 → 接入统一流式展示 → 持续注册文件、业务及外部能力。先建设可用的薄底座，每一层都有具体职责和验证条件；不先编写多个固定业务流程，也不一次建设全部远程设备、连接器市场和多专家系统。

### 14.1 地基中的平台对象

| 对象 | 稳定职责 | 扩展约束 |
|---|---|---|
| Task / Run | Task 表示交办事项，Run 表示一次执行/恢复尝试 | 不强制客户、附件或某种报告；与 SDK session 分离 |
| Resource / Artifact | 输入和输出的统一资源、来源、版本、访问与流转引用 | 二进制文件与结构化内容均可，原始文件不塞进每条模型消息 |
| Capability / Skill | 能做什么、如何做、版本、依赖与允许的执行方式 | 新增能力按契约注册，不让任务核心按业务名称判断分支 |
| Invocation / Receipt | 一次具体工具操作、执行状态、幂等及实际结果/回执 | 区分读取、准备、写入和结果核验，异步受理不冒充业务完成 |
| Interaction / Checkpoint | 提问、决定、确认、答复、已核验阶段和继续条件 | 等待可持久化，不依赖前端连接和某个模型请求存活 |
| Event | 可排序/去重/回放的运行事实与展示投影来源 | 普通文本与特殊组件同一时间线，状态变化与事件可靠衔接 |
| Actor / Grant / ExecutionTarget | 可信运行身份、范围授权、执行位置及能力 | 继承后端真实权限，执行目标初期可只有自有后端一种 |

这些是逻辑边界，不要求每项拆成一个服务或新建一个空目录。Goal、事件触发规则和外部连接配置在后续接入时复用这些对象，不提前做成全部可用的产品功能。设备可作为执行或来源信息，通用 Task 不应仅因最初来自手机就被永久限定为手机专用任务。

### 14.2 统一能力接入契约

能力至少声明：稳定 ID/版本、用途与使用条件、输入/输出 schema、所需资源类型、依赖、运行目标、权限范围、读取/写入及风险策略、超时/重试边界、是否支持准备预览/提交、幂等方式、结果核验或查询方式。

执行结果统一表达：成功且有结果、执行中且可查询、需要补充信息、需要确认、等待依赖、失败、结果不确定。不能把任意 HTTP 200 都翻译成任务完成，也不能让模型自己认定已经写入成功。

后端原生适配、MCP 和后续其他连接方式都转换为这一平台契约。不同方式不要求暴露完全相同功能，适配器需声明实际支持的能力；不重复自建 MCP 标准传输或成熟 SDK 的模型执行循环。

模型按当前授权发现候选能力，加载版本化技能并选择工具；平台在实际调用前校验输入、身份、资源、权限与确认，调用后记录结果并执行必要核验。业务规则由原业务系统负责，技能负责工作方法。新增业务能力可以包含自己的准备与提交逻辑，但不应修改任务通用状态机。

首个连接对象明确为自有后端。MCP 是否作为首个实际传输方式，可在这一契约下独立选择，不把“所有工具先改成 MCP”作为开工条件。

### 14.3 基础设施阶段与完成标志

| 阶段 | 建设范围 | 可检验的完成标志 |
|---|---|---|
| A：统一对象与持久状态 | Task/Run、身份与资源引用、Interaction、Invocation、Event 的最小模型和迁移/兼容方案 | 没有客户或附件也能创建任务；输入引用、运行事实与等待状态能保存和查询；业务与 SDK 类型不进入核心契约 |
| B：能力目录与调用入口 | 能力注册、发现、schema、版本、技能依赖、授权/确认规则、自有后端适配边界 | 两个能力复用相同调用路径；输入无效或无权时明确拒绝；可查明具体调用及结果，不改聊天核心 |
| C：Work 执行与交互 | 复用 SDK 执行循环，增加平台适配；资源按需读取、提问/确认、检查点、取消、恢复和结果核验 | 用受控验证工具覆盖运行→等待→答复→继续→完成，以及断连/重启、重复确认和结果不确定；明确哪些阶段已支持恢复，不宣称任意工具都可安全重放 |
| D：统一流式展示与资源入口 | 事件适配、快照/游标、组件注册表、“+”资源选择、问答/确认/阻塞/结果基础组件 | 实时与历史一致，断线重放不重复；新增组件仅扩展注册和 schema，未支持类型可降级；前端动作绑定后端交互 |
| E：持续叠加能力 | 逐项增加文件解析/生成、业务工具与技能；再按需接外部系统、事件触发和设备 Worker | 新增一项能力不重写 Task/Run、事件协议、交互系统；可从声明追到授权、调用和核验结果 |

阶段是依赖顺序，不要求整层全部做完再做下一层。对象和事件契约确定后，资源、执行适配与前端展示可围绕同一契约增量推进。受控工具只用于验证底座，不作为真实业务已实现的证据；底座可用后再挂入实际业务能力验证适配。

### 14.4 自有 PC 前后端的复用边界

本轮源码核对发现：

- 客户查询和客户 CSV 导入入口已存在，`CustomerController` 复用 `CustomerImportService`；这不能直接证明“CSV 导入线索”已经实现，后者需由线索领域补齐相应用例。
- 线索已有查询、创建、分配和生命周期接口；外呼已有派发接口与 `CallDispatchWorkflowService`，跟进待办已有查询接口。
- 部分权限、归属和业务逻辑仍在 Controller 中。新增 Agent 适配前逐项评估能否安全提取/复用应用用例，由 PC 与 Agent 共用；不复制规则，不跳过原权限，不让模型直连数据库。
- “创建计划任务”“分配给某人/设备”和“立即派发拨号”须按真实业务语义分别声明。不能因为现成接口名称相近，就把用户排任务的意图映射为立即产生外部动作。

初期执行目标是后端业务能力，不要求电脑屏幕保持打开，也不需要先建设远程桌面控制。平台运行身份从可信认证上下文取得，模型不能自报租户/用户决定权限；后台委托调用需落实原用户数据范围与后端审计。

这些查询、创建、批量操作和汇总需求用来检查能力契约的覆盖范围，不据此建立三个专用 Agent 或写死任务流程。

### 14.5 每新增一个功能时的接入清单

1. 查找已有业务用例/成熟工具，明确能力所有者和复用路径。
2. 提供版本化能力声明、输入输出 schema、依赖与执行适配，必要时配套技能。
3. 声明资源、权限、确认、幂等与恢复边界，以及完成核验方式。
4. 将结果适配为现有资源/交互/结果组件；确需新展示才增加组件 schema 与注册。
5. 验证正常、无权、缺资料、失败、重复调用和不确定结果；按实际验证范围标记能力可用。

底座扩展的判断标准是新增能力是否主要落在声明、适配、技能及必要的展示扩展，而非要求后续任何功能都“零代码”。新文件格式需要处理器，新业务操作需要相应用例与适配。
