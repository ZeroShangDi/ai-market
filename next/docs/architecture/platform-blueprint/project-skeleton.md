## 1. 目录结构

```text
ai-market/
├── applications/                         # 业务应用：组合领域能力形成业务闭环
│   └── <app-name>/
│       ├── definition/           # 应用定义、所需能力、配置、角色
│       ├── web/                  # PC 跨模块页面组合
│       ├── mobile/               # 移动端跨模块页面组合
│       └── workflows/            # 跨模块流程，用代码和配置表达
│
├── projects/                     # 三个前端工程 + 一个后端工程
│   ├── web/                      # PC 网页入口、导航、应用挂载
│   ├── mobile/                   # 移动 APP 入口、原生能力、应用挂载
│   ├── desktop/                  # 桌面套壳，复用 Web
│   └── server/                   # 基础 Server，加载应用流程和模块后端
│
├── packages/                     # 共享资源包，按真实复用需要提取
│   ├── ui/                       # 通用 UI、主题、图标等资源
│   ├── contracts/                # 稳定公共协议与基础类型
│   └── sdk/                      # 公共能力调用接口及客户端封装
│
├── modules/                      # 领域模块，具体领域边界待细致分析
│   └── <domain-name>/
│       ├── contracts/            # 本领域公开命令、查询、事件
│       ├── backend/              # 领域规则、用例、数据访问
│       ├── web/                  # 本领域 PC 页面与组件
│       ├── mobile/               # 本领域移动页面与业务任务
│       ├── mcp/                  # 本领域开放工具接口
│       ├── skills/               # 使用本领域能力的 AI 技能
│       ├── connectors/           # 外部系统集成与领域数据映射
│       ├── migrations/           # 本领域数据库迁移
│       └── tests/                # 领域规则及公开契约验证
│
├── docs/                         # 项目文档：架构、业务、接口、使用说明
├── rules/                        # AI 开发规范文档
│   ├── README.md                 # 规范索引及适用范围
│   ├── architecture.md           # 依赖方向与模块边界规范
│   ├── development.md            # 开发、复用、命名等规范
│   └── verification.md           # 验证与交付规范
│
└── ops/                          # 构建、部署、发布、升级等工程运维
    ├── build/                    # 构建脚本、应用装配和兼容检查
    ├── deploy/                   # 环境配置与部署模板
    ├── release/                  # 发布清单、版本与制品管理
```

应用组合直接通过代码和配置定义，不规划可视化组装器，也不设置独立的 `assembler` 工程。构建时需要的装配检查或清单生成归入 `ops/build`。

## 2. 职责与协作

- `projects` 是实际运行的工程。前三个面向用户，后端工程加载公共基础能力、选定模块的后端实现，以及应用定义的服务端流程。
- `applications` 定义产品组合：用哪些模块、如何组合页面、如何衔接业务步骤。它不复制领域规则，也不直接访问模块的数据表。
- `modules` 拥有业务规则与数据，按需提供多端页面、MCP、SKILL、连接器。不能因为存在一个菜单就创建一个领域模块。
- `packages` 存放确实共享的资源或基础能力，不收集业务对象。领域公开契约仍由对应模块拥有。
- 基础能力可直接位于 `projects/*` 内；需要共享时提取到 `packages/*`。不要求所有基础设施先包化。
- `ops` 调度构建、部署、升级；具体数据库迁移脚本仍随所属领域模块维护。

桌面工程复用 Web 页面，只补充桌面系统能力。模块存在专属桌面能力时，再按需求增加相应适配，不默认复制一份 Web 页面。

## 3. 三个容易混淆的边界

| 边界 | 归属 |
|---|---|
| 客户列表等单领域页面 / 客户详情中组合通话和待办 | 前者属于 `modules`，后者属于 `applications` |
| 通用流程执行与恢复机制 / 销售跟进的步骤定义 | 前者属于 `projects/server` 或共享包，后者属于 `applications/*/workflows` |
| AI 如何开发本项目 / AI 如何使用某个业务能力 | 前者属于 `rules`，后者属于 `modules/*/skills` |

`rules` 是规范文档目录，不会仅因目录存在就自动被所有 AI 工具读取。实施时由仓库 `AGENTS.md` 等工具入口引用规范索引；应复用并整合现有《项目规矩.md》，避免并存两套冲突规则。本轮没有创建新的强制规范。

## 4. 依赖原则

1. 工程加载应用，应用组合模块；工程的装配代码可以引用所需模块的公开入口。
2. 领域模块只使用其他模块公开契约，不能依赖某个应用或工程的内部实现。
3. 多端模块通过稳定能力接口使用会话、导航、文件、通知和原生能力，不直接读取入口工程的私有状态。
4. 共享包不反向依赖业务模块或具体应用。
5. 一个模块不必是一个服务。首期使用一个后端工程装载模块；未来有明确需求再调整部署方式。

## 6. 实施顺序

1. 梳理业务流程、规则、数据和事务，确认领域边界。
2. 列出移动端、PC、后端工程对现有路径与框架的依赖，制定迁移清单。
3. 建立 `projects` 入口边界，复用现有公共能力；确认需要共享的部分后再提取 `packages`。
4. 把已确认领域归入 `modules`，把跨领域页面与流程归入 `applications`。
5. 整理 `rules` 和 `ops`，验证 PC 发起、手机执行、结果回填的完整链路。

每一步以可运行和可验证为前提，不一次性创建全部空工程，不在模块边界明确前大规模搬代码。
