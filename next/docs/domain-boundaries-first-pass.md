# 第一轮领域边界分析：外呼业务闭环

日期：2026-10-13。状态：基于现有源码的初步分析，尚未迁移实现、运行测试或完成全业务领域划分。

本轮从“PC 发起外呼 → 手机执行 → 结果回填 → PC 查看”开始。只读分析旧工程，所有产出位于新架构临时根内。

## 1. 第一版结论

1. 通话派发、接受、状态、结果、录音和去重属于一组紧密相关的通信能力，先作为一个候选领域整体处理。
2. 客户和线索是否允许联系，应由它们所属业务负责判定；通信代码不应直接读取其 Mapper/实体。客户与线索是否合为一个关系管理领域，仍需分析线索转化、归属变更和跟进生命周期。
3. 通话完成后的线索活动记录、客户跟进任务属于业务应用的跨能力组合；目前它们与通话完成处于同一数据库事务。第一轮迁移必须保留这一行为，不直接改成异步事件。
4. 设备身份、会话、安全存储是基础能力候选；“哪个设备可执行外呼、解绑后哪些派发失效”是通信规则。不能把整个设备目录全部归平台。
5. 先区分代码职责并复用现有实现，不拆服务，不确定新框架，不预建所有领域目录。

## 2. 链路与规则

| 步骤 | 当前行为与证据 | 建议归属 |
|---|---|---|
| PC 选择联系对象和手机 | PC API `createCallDispatch`；后端要求客户/线索二选一、来源匹配、对象属于当前员工且状态可联系，设备已配对且最近在线 | 页面组合归应用；对象规则归客户/线索所有者；设备执行资格归通信 |
| 创建派发 | `CallDispatchController.create` 先处理同幂等键重放与载荷冲突，再检查可变对象状态；新派发保存号码快照，5 分钟有效，状态为 queued | 通信用例，不能留在 Controller |
| 手机获取派发 | `foreground.ts` 检查会话、设备凭据和前后台运行条件，刷新心跳、拉取派发、自动接受；当前后台条件直接关联手机宠状态 | 通信移动任务使用宿主生命周期/后台能力接口；手机宠不成为通信领域依赖 |
| 手机接受派发 | `CallDispatchWorkflowServiceImpl.accept` 再次检查客户/线索归属和状态；条件更新 queued → accepted，同事务创建通话、移动事件、派发事件 | 通信事务；联系对象判定通过公开端口调用，保留接受时再次检查 |
| 真正拨号 | `calls.ts.beginCall` 阻止并行/未结束通话，先获取服务端通话标识和号码，再调用原生 dial；区分未启动与状态不确定 | 通信移动任务负责顺序和锁；原生桥接由工程提供 |
| 保存结果 | 手机先保存待同步任务和必要录音副本，再同步结果；记录 event ID、幂等键与上传 ID；未安全保存不能宣称成功 | 通信拥有任务内容、重放语义；安全存储等机制由基础能力提供 |
| 后端完成通话 | 校验设备、员工、事件指纹、可完成状态、时间与时长，更新通话并保存完成事件；条件性写线索活动或客户跟进任务 | 通信负责通话规则；跨能力副作用由应用用例协调，首期保持本地事务 |
| PC 查看结果 | 通话页面查询派发/记录；通话统计服务还直接查询 `cp_follow_up_task` | 通话查询归通信；跨领域指标由应用查询组合 |
| 上传录音 | 移动适配器提供独立上传入口，调用录音存储服务；录音同步可以晚于结果保存 | 录音归属、访问和状态归通信，存储介质与加密机制按需共享 |

不要把“派发已接受”等同于电话已接通，也不要把“结果已保存”等同于录音已上传。

## 3. 数据归属候选

| 数据 | 初步所有者 | 备注 |
|---|---|---|
| `cp_call_dispatch`、派发事件 | 通信 | 派发状态、请求快照、有效期 |
| `cp_call_record`、`cp_mobile_call_event` | 通信 | 通话事实、状态和事件去重；移动事件表不自动等于通用事件总线 |
| `cp_call_recording_asset`、录音访问审计 | 通信 | 录音业务归属和授权；不能因是文件就全部交给基础设施 |
| `cp_customer` | 客户业务所有者，具体模块名待定 | 联系资格和数据归属通过公开接口提供 |
| 线索及线索活动 | 线索业务所有者，具体模块名待定 | 与客户的领域关系需检查转化事务后确定 |
| `cp_follow_up_task` | 暂归客户跟进业务边界候选 | 未证明存在跨业务的通用任务需求，不先拆独立任务领域 |
| `cp_device`、配对码 | 现有混合结构，暂不拆表 | 身份/凭据机制与通信设备资格先分接口职责，再判断数据拆分 |

以上是责任归属建议，不是已经存在的独立模块。数据库物理拆分不在本阶段范围内。

## 4. 必须先解决的耦合

| 已观察到的事实 | 改造方式 | 不能丢失的行为 |
|---|---|---|
| 通信 workflow 直接依赖 CustomerMapper、LeadMapper | 引入联系对象资格端口，由对象所有者提供实现 | 创建时检查、接受时复查、租户/员工范围、有效状态 |
| HTTP Controller 承载派发创建和完成事务 | 把完整用例移到应用服务，Controller 只转换协议 | 幂等处理顺序、并发条件更新、事务原子性 |
| V1 移动适配器调用另一个 Controller | 两套 HTTP 适配调用同一应用用例 | 旧路由/字段/错误语义在兼容期保持 |
| 通话完成直接写线索活动与客户跟进任务 | 应用协调明确的领域公开操作 | 先保持同事务，去重不能只覆盖通话却重复创建跟进 |
| 通话统计通过 SQL 查跟进表 | 应用组合通信统计与跟进查询 | 数据权限、时区和统计口径一致 |
| 前台轮询依赖手机宠开关 | 工程实现后台执行能力接口，通信任务只读能力状态 | 不把后台尝试运行描述为可靠常驻 |

注意：现有接受派发时虽在事务内查询客户/线索，但本轮没有证明它与并发归属变更严格串行化。迁移前需补充并发用例，不能仅凭 `@Transactional` 宣称没有检查与执行之间的竞争窗口。

## 5. 第一个试点的范围

**主线：**已有有效登录与设备配对 → PC 为可联系客户创建派发 → 手机接受并拨号 → 保存结果 → PC 查看。

**兼容场景：**线索外呼、预设下次跟进时间、设备撤销、离线结果恢复、录音延迟上传。可以分阶段接入，但不能把这些已有行为静默删除后宣称完整迁移。

**暂不纳入：**AI 总结、企微、拓客、可视化组装器、服务拆分、框架替换。它们不作为证明第一条闭环成功的前提。

## 6. 最小契约草案（仅列职责，尚未定 schema）

| 契约/端口 | 提供方 | 关键要求 |
|---|---|---|
| 查询/校验可联系对象 | 客户或线索所有者 | 对象类型与 ID、权限上下文、可联系性、必要号码快照；不输出 ORM 实体 |
| 创建/接受/取消派发 | 通信 | 明确状态转换、有效期、幂等键与冲突语义 |
| 完成通话 | 通信 | 校验设备、员工、事件指纹与时间；重复提交返回一致结果 |
| 记录线索联系/创建客户跟进 | 所属业务能力，由应用协调 | 可参与本地事务，明确去重与失败策略 |
| 查询通话与录音访问 | 通信 | 数据范围和归属校验，不能只靠前端隐藏 |
| 会话、时间、原生拨号、安全保存、生命周期 | 工程或共享基础包 | 通信移动任务通过接口使用；类型不能依赖某个框架私有状态 |

下一步把这些职责落实为输入/输出、状态、错误、幂等、事务和测试例子，不先建设通用插件协议。

## 7. 迁移顺序与验收

| 批次 | 实施内容 | 验收门槛 |
|---|---|---|
| A | 补查线索转客户、客户归属变更、跟进生命周期与设备会话代码，完善边界 | 明确谁拥有规则，标明未决问题；不创建候选空模块 |
| B | 定义上述最小契约、状态表和行为基线 | 每个接口都有成功、拒绝、重试、并发场景 |
| C | 在临时根建立实际选定工程，迁入基础依赖与完整用例 | 只在临时根构建，业务实现不依赖旧工程运行路径 |
| D | 接入 PC 和手机链路，保持关键事务与恢复机制 | 接受竞争仅生成一个通话；完成重放不重复产生跟进/活动 |
| E | 补齐兼容场景和真实设备验收 | 会话切换、设备撤销、断网恢复、录音延迟均有证据 |

需要保留的行为基线：

- 同幂等键同请求重放返回原结果；不同载荷明确冲突。
- 创建后对象归档/转移，接受时再次判定；并发变更行为另行核验。
- 过期、取消、撤销设备不继续启动新派发。
- 接受与取消竞争、重复接受不生成多条通话。
- 原生拨号超时不能盲目重拨；未结束或结果未安全保存不能失去保护。
- 结果重复回填不重复产生业务副作用；不一致事件指纹拒绝。
- 结果和录音分别恢复，同一会话身份下恢复原任务；不能跨租户/用户重放。
- 跟进创建失败时维持当前事务语义；若未来改成异步，需明确新的产品行为和补偿策略。

已有测试包括派发工作流、创建幂等/重放、移动协议、跟进任务构建、通话时长和录音存储，可作为后续测试迁移候选。本轮仅定位和部分阅读，未执行，不据此宣称链路已通过。

## 9. 本轮留下的待核实问题

- 客户与线索是一个限界上下文的不同阶段，还是应保留为两个领域？需读取完整转化与归属变更用例。
- 跟进当前是否只服务客户/线索？没有跨领域复用证据前，不建通用任务模块。
- 设备配对是否已有非通信业务消费者？没有证据前，不抽象为完整设备平台。
- 号码在创建派发后变更时，按快照还是最新值拨打？当前派发保存号码快照，需确认其业务预期。
- 当前并发归属变更、接受派发与撤销设备的竞争行为，需要后续验证。

本报告只支持外呼切片的初步边界，不作为全项目领域划分的最终结论。
