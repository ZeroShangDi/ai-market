# 可选支付模块

已按用户选择采用「各应用独立商户」。复用原 yudao-module-pay 和原支付应用、微信/支付宝渠道、支付单、退款单、通知任务页面。支付应用拥有自己的渠道商户号、证书和密钥，不设置跨应用默认商户；业务订单、商品、权益和财务核算仍归业务模块。

## 简单装配

支付是可选 Maven 模块，默认公共后端不包含支付 SDK。使用 `mvn -f container/backend/pom.xml -Ppayments package` 构建，并启用 `container,payments` 运行配置；按顺序导入公共 schema/common-data/app-release 和可选 `backend/sql/payments.sql`。没有复制原商户、密钥、账单或示例资金数据。

本机可执行 `python3 container/acceptance/start.py --with-payments`，已有同配置构建再加 `--no-build`。运行器核对构建包和功能配置，防止菜单显示但后端模块缺失。去掉可选参数重新构建启动即可移除支付模块和入口，数据保留。

## 归属与边界

- 支付模块单向依赖 system 和公共框架，system/infra 不依赖 pay。原 Java API 保留，业务模块可按编译模块接入；公共层不导入具体业务实现。
- 支付应用、渠道、支付单、退款、通知及内部存储统一受租户过滤。原部分全局 BaseDO 已改为 TenantBaseDO；原始业务关联继续使用 appId。普通业务 OAuth 令牌不能访问支付管理接口，也没有获得下单、退款的通用 scope。
- 渠道绑定存在的应用，不允许通过更新改绑应用；应用仍有渠道或订单时禁止直接删除。管理页面需要原 pay 权限，独立应用不因共用登录就取得商户配置权限。
- 每个支付应用分别填写自己的商户配置。程序不验证商户的法律归属，也不会仅凭输入的商户号保证真实独立；重复使用另一个应用的凭据仍需运营方禁止。若需要平台自动执行「同一真实商户不得跨应用复用」，应先确定微信/支付宝各自的商户标识模型再加约束。
- 钱包、充值、提现、转账和模拟支付没有公开入口；模拟/钱包渠道不能创建，工厂不注册这些客户端。保留的内部兼容类型不等于对外提供这些资金产品。
- 支付日志不记录配置、签名、请求/回调正文。渠道配置仍沿用原受权限保护的服务端存储，不随客户端分发；备份、数据库访问和密钥托管属于生产部署边界。

## 当前可验收范围

原支付管理页面与接口可运行，应用/渠道配置可真实保存，支付/退款/通知记录可查询；没有伪造成功账单。接口 5 项、浏览器 3 项，以及内部 Java 调用保护 4 项通过，覆盖权限、跨租户、渠道改绑、误删和资金关闭。

`yudao.pay.transactions-enabled` 默认 false。HTTP 与服务层双重拒绝资金写入和对账/通知等触发，内部模块调用也不能因绕过页面而开始扣款。当前环境没有真实商户配置，未连接微信/支付宝，未扣款、退款或转账。

真实收付款尚未开通。启用前还需真实商户和证书、可信 HTTPS 回调域名、业务回调的出站地址白名单与鉴权、幂等及金额/订单归属核对、资金操作授权、平台沙箱和真商户联调。此次没有把这些外部条件称作已经验收。

官方 SDK 继续负责各平台验签与协议处理，不自行替代密码算法。参考 [微信支付官方 Java SDK](https://github.com/wechatpay-apiv3/wechatpay-java)、[支付宝官方 Java SDK](https://github.com/alipay/alipay-sdk-java-all)。当前抽离沿用原工程的渠道 SDK 适配层，正式接入时须核对对应平台的当前协议和商户资质。
