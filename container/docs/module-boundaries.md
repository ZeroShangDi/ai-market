# 公共底座与模块接入边界

公共能力仍然属于独立的 system、infra 和 framework；本轮增加页面与装配，没有把 CRM、ERP、通话或 AI 的业务逻辑合并进公共层。原项目未修改。当前支持两种简单接入，不引入安装器、模块商店或复杂版本体系。现阶段的「应用定义」就是后台菜单、独立地址和角色授权，不是已经实现的统一应用安装包。

## 已抽离的能力归属

| 能力 | 归属和边界 |
|---|---|
| 短信 | system 的渠道、模板和发送日志，沿用渠道适配器和异步发送；业务通过发送服务传模板编号和参数，不自己读取供应商密钥 |
| 邮件 | system 的账号、模板和发送日志，沿用 SMTP 与异步发送；供应商账号不进入客户端或业务菜单定义 |
| 第三方登录 | system/social 的应用配置和用户关联；保留平台、管理端/会员端及租户语义，未将微信等 SDK 放进业务模块 |
| 应用授权 | system/oauth2 的客户端、令牌管理和原 /sso 授权页；每个独立应用有自己的客户端密钥和登记回调，不转发壳子令牌 |
| 地区 | system/area 与 framework/ip 的本地地区树和 IP 数据，仍是公共参考数据，不增加业务表依赖 |
| 监控 | infra 的 Redis、Druid、Spring Boot Admin、链路追踪入口；运行环境级监控不混入租户业务数据接口 |
| WebSocket | framework 提供传输、会话和发送器；容器装配层提供管理台权限校验，业务消息仍应由自己的模块监听器处理和授权，不能默认继承管理台通信权限 |

短信、邮件的渠道/账号/模板及部分日志、OAuth2 客户端沿用原代码的全局公共资源（部分实体带 TenantIgnore），不是“每个租户或应用独立存一份”。它们需要单独授予管理权限，不能把有业务账号等同于有公共配置管理权。社交应用配置保留原 tenant_id。数据库凭据仍由部署环境提供，第三方凭据仍按原服务实现存储，未新增密钥保险库或租户独立密钥机制。

后台方法权限保留，新增菜单不会自动给普通角色授权。地区树是登录后的非敏感公共参考数据。监控沿用独立运维账号，验收环境随机生成强密码，不再使用 admin/admin；业务登录令牌不能代替监控账号，监控账号也不能登录业务 API。Actuator 只开放健康、信息、指标、线程栈等已配置端点，不开放 env、heapdump 或关闭服务操作。Druid 禁止重置统计。

服务和数据库监控使用固定、受信任的内置路径 /admin、/druid。它们可以嵌入本机壳子，但这种信任不授予业务页面。通用业务 iframe 仍拒绝同源和带令牌、凭据的入口；未配置 SkyWalking 时明确显示未配置，不连接上游的公共演示实例。

管理台 WebSocket 使用当前访问令牌，地址栏不展示令牌，默认不自动连接；校验来源、管理端身份、infra:websocket:query 权限及租户。收发时重新校验会话，已退出令牌不能继续通信；单发、群发都按租户过滤，消息不进入诊断日志。当前单实例使用 local 发送器，不能把它当作已经完成的分布式集群总线。以后独立业务的实时连接应使用自己的业务端点和消息命名空间；不要把任意业务消息塞入管理台测试消息类型。

## 方式一：保留芋道原模块，编译接入

适合沿用本仓库原 Java/Vue 模块的业务：

1. 保留独立 yudao-module-xxx Maven 工程、Java 包、API/服务/数据访问层及业务表前缀，在 container/backend/pom.xml 声明模块，在 server/pom.xml 仅增加模块依赖。依赖公共 system/infra API，不反过来让公共模块依赖业务模块。
2. 将对应 PC 页面、接口放进 views/<业务域>、api/<业务域>，原组件需要的依赖也按模块补齐。原动态路由继续根据菜单 component 加载这些构建时页面。
3. 按模块显式导入自己的建表和菜单数据，授予角色权限；不要导入旧账号、密钥、连接配置或整份旧产品数据库。
4. 停用入口时关闭菜单或撤销角色权限；移除运行能力时移除模块装配并重启。数据不会自动删除。

这是代码与包的模块化，同一 JVM、同一 PC 构建、通常同一数据库，不是进程隔离、热插拔或故障隔离。前端新增源代码需要重建；删入口不会自动卸载后端服务。这与原芋道单体的模块边界一致。

已核对原仓库直接 Maven 依赖：

| 原模块 | 接入时必须一起考虑的模块 |
|---|---|
| ERP、MES、WMS、支付、报表 | 直接依赖 system（及公共框架） |
| FMS、IM、会员、公众号、PMS | 直接依赖 system、infra；IM 等业务实时通道还需保留自身端点和授权，不能直接借用受限管理台通道 |
| BPM | 直接依赖 system，需保留原流程组件及相关依赖 |
| CRM、OA | 还依赖 BPM，不能只复制自己的页面就认为完整接入 |
| HRM | 依赖 system、BPM |
| 商城 | 聚合商品、促销、交易、统计、交易 API；应按内部依赖整体核对 |
| IoT | 聚合 core、biz、gateway；网关运行边界不能并入普通公共服务 |

这些是源码依赖核对结果，尚未将上述业务模块迁移或逐一验证。不能承诺每个模块只加一行就立即可用。原 AI、通话、Agent、语音服务不会因此自动重新启用。

## 方式二：独立应用，通过入口接入

适合独立开发、部署、数据库或技术栈不同的业务：

1. 独立部署业务后端和各端页面，在原「菜单管理」登记独立 HTTP(S) 来源，按角色授权。需要 PC 嵌入时使用原 ?_iframe=1 标记。移动端从同一授权菜单生成应用入口。
2. 公共后端只提供自己负责的接口；业务后端校验自己的权限，保有自己的数据，不直接操作公共表。隐藏菜单只影响导航，不能代替后端授权。
3. 可以保持独立登录，也可以使用已恢复的 OAuth2 授权码流程：在应用管理登记专属客户端与精确回调；进入 /sso?client_id=...&response_type=code&redirect_uri=...&scope=...&state=...，服务端用客户端凭据换令牌。原实现换码也需要传 state；客户端密钥不应放进公开前端。
4. 业务服务校验令牌有效性、clientId、tenantId、userType、所需 scope 和自己的业务权限。原公共 API 的角色检查与 scope 检查是不同机制，不会因为声明一个 scope 就自动将所有旧接口限制成对应 scope；需要最小权限服务接口时应明确增加该接口的 scope 校验。
5. 停用菜单不会删除应用服务和数据；独立服务停机也不会卸载公共服务。需要完整移除时由部署者停止对应服务。

授权码签发、独立客户端换码、错误回调和授权码重放已用真实后端验证；新增业务应用自己的回调、服务端会话和业务权限仍需在接入时完成，不是自动安装后的单点登录。PC iframe/WebView 不加载任意后台代码。移动原生新增插件、权限或原生 API 仍需要重新构建安装包，网页菜单不能热安装原生能力。

当前优先原则：原芋道模块按方式一保留；已独立开发的应用按方式二接入。二者复用公共底座，但不强行改造成同一种插件包。

公共依赖方向可运行 `python3 container/acceptance/boundary_check.py` 检查；它限制的是公共层，server 装配层仍可在后续显式加入业务模块。

## 可选支付与更新发布

支付以 `payments` Maven/运行配置装配，仅向 system/公共框架依赖；通用 system/infra 不反向依赖支付。支付存储补齐租户字段；支付应用与渠道不能任意改绑。业务订单不进入公共模块。独立业务 OAuth 令牌默认不能访问支付管理，详见 payment-scope.md。

更新发布为 infra 的独立运维能力，发布表按应用/平台/ABI/渠道组织，不是业务租户数据；授予应用版本管理权限意味着可管理整个基座的发布，不能把该权限分发给普通业务应用。私钥留在可信构建机，公共更新不依赖业务登录。若以后需要应用团队分别管理发布，需再增加发布应用的管理授权，不能用前端筛选代替。

独立应用部署必须使用不同主机名，而不只换端口；Cookie 不按端口隔离。同机 5200 是受控测试来源，不是生产安全分区。公共 Token API 统一经隔离 Cookie 的代理，监控会话不向业务应用转发；跨域来源使用显式清单，不允许读取监控。
