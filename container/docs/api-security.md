# 共享公共接口的安全边界

加密传输和应用授权是两件事。对外统一使用 HTTPS/TLS，不再自创一层前端 AES 或把固定密钥塞进 APK。浏览器代码与公开安装包不能保密共享密钥，也不能只凭 appId、User-Agent、来源头或 CORS 证明请求来自自家软件。[RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) 明确将这类原生应用视为公开客户端。

本轮可落实的结构：用户登录走原平台，独立应用后端/BFF各自持有 OAuth 客户端凭据，通过授权码获取用户授权；敏感公共接口再由应用后端调用。浏览器和手机不保管服务端客户端密钥。后端调用公共服务时使用每个应用独立的客户端证书；吊销某个应用不需要更换所有应用的密钥。

## 已落实的代码和部署模板

- 令牌身份现在携带数据库签发的 clientId，不相信调用方自己填写的应用请求头。非 default 的应用令牌不能因为用户是超级管理员就访问整个管理后台。
- 独立应用只可访问明确列出的个人资料、可见配置、本人通知及上传接口，而且必须具备相应 user.read、config.read、notify.read、notify.write、files.write scope。原后端方法权限和本人/租户检查继续执行。新增公共接口必须显式列入策略，不默认全部开放。
- 复用 Redis 限流，在安全链之前按实际来源/IP和固定类别计数，改变密码、参数、伪造转发头不会新增无限个桶；超限返回429，Redis不可用则返回503。正常配置认证30次/分钟、API600次/分钟；隔离自动验收环境使用单独高额度，不代表生产策略。
- deploy/nginx.conf 提供实际 HTTPS、登录/接口限流、查询参数不落访问日志、WebSocket升级、监控代理，以及独立的后端调用主机。service-api 需要可信CA签发且指纹被明确登记的客户端证书。
- 启用 container,edge 配置时，网关从已验证证书指纹映射 OAuth clientId，覆盖 X-Container-App；基座比对证书对应的应用和令牌/Basic客户端。公开管理入口清空该头。后端仍只监听回环地址，不允许客户端绕过网关直接提供这个头。

部署模板中的域名、证书、CA和指纹映射必须换成自己的值；私钥、CA材料不入 Git。证书是给服务端/BFF使用，不能复制进所有手机安装包。生产由可信代理覆盖来源头；不能直接信任任何公网请求的 X-Forwarded-For。

## 仍需分清的范围

默认客户端是当前壳子自己的第一方登录；对外入口仍须有验证码、账号权限与限流。TLS保护网络中的内容，scope限制应用可调用的能力，角色/租户/对象检查限制用户能操作的数据，三者互不替代。公共文件仍沿用持URL可读方式；敏感附件必须另用对象授权接口或短期签名下载，不能当作已解决。

应用后端的授权码流程已存在；公开手机/SPA需要PKCE的场景尚未实现，不能把现有“客户端密钥换码”直接打包进手机。新的公开客户端登录应按[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)支持S256 PKCE、精确回调、state及最小权限。采用原芋道扩展还是独立认证服务属于后续较大的身份架构决策，本轮不偷偷替换现有登录。

无法承诺“所有仿冒客户端都无法发请求”。对于公开手机可进一步用设备密钥、平台完整性证明和风险策略提高仿冒成本，但具体依赖应用分发平台，不默认强制绑定Google Play或苹果服务。对公网大流量攻击仍需要边缘防护；[OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/)也要求限制资源和第三方服务调用成本，不能只依赖业务密码。

## 本机实测

真实 Nginx HTTPS/mTLS 6 项通过：严格验证服务端证书，缺少或未登记客户端证书拒绝，证书映射应用与令牌不一致拒绝，伪造应用头被网关覆盖，scope/用户权限与停用应用继续生效。独立后端与 Redis 库的限流 3 项通过，实际返回 429 和 Retry-After。临时测试 CA、私钥和容器在测试结束后清理。没有配置正式域名或公网部署。

异常及 JSON 解析日志只记录错误类型和代码位置，避免将渠道配置、SQL 参数、请求正文或提供方错误原文写入诊断；错误日志仍保留定位所需的调用位置。

## 浏览器与监控会话

业务 Token API 的代理不转发 Cookie，也不把 Set-Cookie 写回浏览器；开发代理和 Nginx 模板保持一致。监控页面保留独立 HttpSession、CSRF 和 ADMIN_SERVER 角色。这样业务页面的并发刷新不会轮换监控会话；不能为修复这一问题关闭会话固定攻击防护。生产后端保持回环监听，外部请求通过此代理。

CORS 改为 `CONTAINER_BROWSER_ORIGINS` 精确来源清单，拒绝通配符和带凭据地址；业务跨域调用使用 Token，不带 Cookie。开发仅登记 PC5188/移动5190，edge 默认只同源，需要直接跨域浏览器调用时才显式增加可信来源。监控 /admin、/druid、/actuator 不允许任何跨域读取，包括登记的业务来源。CORS 只是浏览器边界，不能替代服务端鉴权。

业务页面使用独立主机名部署；不能只靠不同端口隔离 Cookie。同主机不同端口虽然属于不同 Origin，仍会共享主机 Cookie。禁止把运维会话所在主机上的另一个端口当作不可信业务隔离区；本机5200仅为受控验收夹具。

认证持久化采用 [Spring Security 会话仓库](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html) 的独立上下文做法，业务身份与监控会话分开。
